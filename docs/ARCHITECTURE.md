# Kynex architecture

Plain-language version: the "Architecture & security" tab of the Kynex Google Sheet.

## The four pieces

```
 Phone / laptop browser (installable web app)
 ┌──────────────────────────────────────────┐
 │ artifacts/web      screens only          │
 │ lib/motion         camera engine         │  video never leaves the device
 └──────────────┬───────────────────────────┘
                │ https, JSON, contract = lib/api-spec/openapi.yaml
 ┌──────────────▼───────────────────────────┐
 │ artifacts/api-server                     │  every rule and permission check
 └──────────────┬───────────────────────────┘
                │ lib/db (Drizzle ORM)
 ┌──────────────▼───────────────────────────┐
 │ PostgreSQL (Replit now; India region      │
 │ before real patients)                     │
 └──────────────────────────────────────────┘
```

| Folder | What it is | Rules |
|---|---|---|
| `lib/motion` | Camera engine: landmarks to angles, reps, form checks for 25 exercises. | No screens, network or database. Pure functions, unit-tested. |
| `lib/api-spec` | `openapi.yaml`, the contract between apps and server. | Change the contract first, then `pnpm codegen`. |
| `lib/api-client-react` | Generated React Query hooks for screens. | Never edit `src/generated` by hand. |
| `lib/api-zod` | Generated validators the server uses on input and output. | Never edit `src/generated` by hand. |
| `lib/db` | Database connection and table definitions. | See "Database rules" below. |
| `artifacts/api-server` | Express server. Only thing that touches the database. Serves the web app on the same address. | Every route validates input and checks permissions. |
| `artifacts/web` | Vite + React screens, installable on phones (PWA). | No business rules. Wrapped into store apps later with Capacitor. |

## How a camera exercise runs (M5c)

1. **The box.** The camera screen shows a box: tall for standing and sitting exercises, wide and low for floor
   exercises (`boxFor` in `lib/motion`). Counting starts only when the whole body (head to feet; seated: head to
   knees) has been inside it, in the exercise's starting position (upright, or lying / on all fours), for 1 second.
   Leaving the box for more than 0.6 s pauses counting and drops the rep or hold under way. This stops walking to
   the mat from counting as reps, and makes people stand far enough back for their feet to be seen.
2. **Only complete reps count.** A rep that isn't complete (not far enough, or the end position not held) is
   recorded as "not complete" and the patient is told why and asked to do it again.
3. **Sounds and words.** Each meaning has its own sound (in place, out of the box, form problem, rep counted, not
   complete, timer reset, done), generated in the browser (`artifacts/web/src/lib/sounds.ts`, no sound files).
   Nothing is spoken during a rep; after it, one line: the count, the count plus one correction, or "not complete"
   with the reason (`VoiceCoach` in `lib/motion`). Holds count down with a big amber ring and start again if the
   position breaks.
4. **Form rules that depend on the camera angle** (e.g. heels lifting with the phone on the floor) compare with the
   person's own resting value instead of a fixed limit (`FaultRule.measure` / `rise`).
5. Every rule change is checked by replaying real phone recordings through the engine (MediaPipe landmarks →
   tracker) before and after.

## Database rules

- `id` is a random UUID primary key.
- Every row that belongs to a clinic has `clinic_id`.
- `created_at`, `updated_at`, and `created_by` where a person made the row.
- Status-like fields are text validated by the API, not Postgres enums.
- Derived values (adherence, alerts) are computed when read, not stored.
- Migrations are SQL files generated by `pnpm --filter @kynex/db generate`, logged in `docs/DATABASE_SCHEMA.md`, reviewed in the pull request and applied automatically when the server starts.

## Security baseline

- Video is analysed on the device; only numbers reach the server.
- Strict security headers in production (CSP, HSTS, no framing, camera only for our own pages).
- API rate limit (300 requests a minute per address), 100 kB request body limit (4 MB for a finished exercise with its movement track).
- Errors never send internal details to the browser.
- Secrets only in Replit Secrets / environment variables, never in the repository.
- GitHub Checks (type checks, tests, build, dependency audit) must pass before merging; Dependabot proposes security updates.
- Sign-in (M1): passwords hashed with scrypt (built into Node, no extra package); sign-in held in an
  `HttpOnly`, `Secure`, `SameSite=Lax` cookie (`__Host-` prefix in production) whose token is stored only as a
  SHA-256 hash; 5 wrong passwords lock an account for 15 minutes, plus 20 sign-in attempts per 15 minutes per address;
  changes (POST) coming from other websites are refused.
- Every API route checks the signed-in role on the server and only reads its own clinic's rows; automated tests
  prove patients and clinicians can't open admin routes.
- Body tracking (M2): Google's MediaPipe pose model (Apache-2.0) runs in the browser. Its runtime and model are
  served by Kynex itself (`/mediapipe`, `/models`), not a third-party CDN; the model is pinned to one version and
  checked against a SHA-256 fingerprint at build time (`artifacts/web/scripts/pose-assets.mjs`). The production
  CSP adds `'wasm-unsafe-eval'` so this WebAssembly can run; it does not allow JavaScript `eval`.
- Voice (M2): the phone's built-in speech, spoken on the device; no text is sent anywhere. M4 swaps it for
  pre-recorded natural voice files.
- Session video (M4): the camera video of each exercise is recorded and kept **only on the patient's phone**
  (the browser's own storage, IndexedDB) and replayed there with the body outline. The server receives the counts,
  rep-by-rep results and the movement as joint positions (no picture, no face); the doctor sees that as an animated
  figure. Clearing the browser's site data deletes the phone's videos.
- Who sees what (M3-M5b): patients see only their own plan, sessions, reports and visits; a doctor sees only their own
  patients (anything else answers "not found"); the admin sees the whole clinic. Every plan change, session, symptom,
  review, note and booking is written to an append-only `activity` log (who, what, when).
- Bookings (M5b): all times are clinic time (India); the server checks working hours, leave, holidays, the 10-minute
  gap between visits, double booking of doctor or patient, the 60-day limit and the patients' 12-hour cut-off.

## Avoiding lock-in

Only standard Node, Postgres and environment variables are used. Nothing depends on Replit-only services, so the app can move to another host or an India-region database by changing `DATABASE_URL` and the deploy commands.
